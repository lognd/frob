# frob-v2 structural audit, 2026-10-07

Branch experimental at 3c0c6a64b. Read-only audit: no build, no commit.
Scope: crate graph vs docs/design/boundaries.md, build and test cost,
correctness risks (ledger, leases, land, worktrees, portability), CI/CD,
design drift, ticket backlog, plus (owner scope change mid-audit) the
code-level structure: decoupling, abstractions, efficiency and how
straightforward it is to program in this repository.

Evidence numbers below come from `cargo metadata --no-deps --offline`,
`wc -l`, `gh run list` / `gh api .../jobs`, and
`target/debug/frob ticket list --json`.

Severity rubric: HIGH = data/security loss or a bypassable control;
MEDIUM = real bug or real structural cost with a bounded blast radius;
LOW = correctness/accuracy nit or cleanup.

---------------------------------------------------------------------

## HIGH

### H1. Windows CI has been red for 30+ hours and 20 lands went onto the red base; nothing in the land path looks at CI

- Area: CI/CD, land gate.
- Evidence:
  - `gh run list -w ci`: last green run 2026-10-06T16:25:34Z; every
    run since (20 of 20 sampled, 2026-10-06T16:41Z to 2026-10-07T17:15Z)
    is `failure`. Every failing run is the job `rust (windows-latest)`,
    step `nextest (Windows, isolated tool)`, test
    `gob-macros::ui_rule_attr ui_rule_attr` (jobs 112386550869 and
    112916759571; FAIL after ~201 s).
  - `git log --since=2026-10-06T16:25:34Z`: 231 commits, 20 of them
    `tickets(land)`.
  - The bug ticket ~1ZE1H1X was filed 2026-10-07T16:57, about 24 hours
    after the first red run, so the red was not noticed by any gate.
  - `dev-publish` (ci.yml:157-160) needs the rust job, so the dev
    prerelease channel has not been refreshed since 2026-10-06.
  - D102 (README.md:187) makes the pre-hand-off `cargo dev ci` through
    goway the Windows gate, but goway offload is Linux only:
    build-test-ci.md section 4 ("a Windows host (`--remote-os windows`)
    is one more variant there, deliberately not built"), and
    `clippy-windows` is a cross-check that does not run tests.
  - frob-gh (crates/frob-gh, "CI status" in boundaries.md 2.2) exists
    and has zero reverse dependencies, so no verb can read CI state.
- Failure scenario: implementer runs `cargo dev ci` (Linux, green),
  coordinator lands; the windows-latest job fails; the next 19 lands
  pass every local gate and land on top; a Windows-only regression in
  any of those 19 would be masked by the already-red job, and the
  shipped Windows archive is whatever the last green run built.
- Consequence: the only real-platform gate for a shipped target is
  effectively disabled; D102's "revisit when a second Windows break
  reaches experimental" trigger cannot fire because nobody observes the
  first one.
- Recommended change (smallest bounded first):
  1. `frob land` reads the head-of-base CI conclusion through frob-gh
     (`[land] require_base_green = true`): refuse with a named code when
     the base's latest `ci` run on the configured workflow is red,
     Unresolved (not pass) when it cannot be read. This wires the
     orphan frob-gh crate (M11) into frob-land.
  2. Until then: a coordinator step "gh run list -w ci -L 1" before each
     land batch, written into notes/coordinator.md land recipe.
  3. Add `goway run --host win` for the nextest step of `cargo dev ci`
     (RemoteOs::Windows variant), or keep a short Windows-only smoke
     subset that implementers must run.

## MEDIUM

### Correctness

#### M1. `land` can exit 4 after the ticket is already closed (~BWMVSPZ): no point-of-no-return discipline, bare branch names, git errors classified as internal

- Where: crates/frob-land/src/land.rs `Ready::publish` 217-317,
  `ledger_step` 923-970, `advance` 840-903; crates/frob-land/src/error.rs:91.
- What is wrong:
  - After `advance` moves the base, later steps still propagate with
    `?`: the trunk-mode `ledger_step(...)?` (land.rs:270-279) runs after
    the base already advanced; its `rev_parse(base)` fallback
    (land.rs:933-935), `append_land`, `record_exemption`, `close`,
    `record_bypass` can each fail and turn a published land into a
    non-zero exit.
  - The base is always resolved by its short name (`"experimental"`):
    land.rs:122, 199, 817, 845, 935, 1032; gob-git read.rs:154 passes
    it to `gix::rev_parse_single`, which DWIM-resolves the name through
    the ref search list on whatever ref snapshot the long-lived `Repo`
    handle holds. Elsewhere in gob-git (`check_local_edits`,
    ledger.rs:324) a `fresh_gix()` is taken precisely because a cached
    handle went stale; land holds three handles (`repo`, `wt`,
    `site.ledger.repo()`) across minutes and across other processes'
    `git branch -D` / `update-ref`.
  - `LandError::Git(_) => CliError::internal` (error.rs:91) maps an
    environmental git failure to E-INTERNAL, exit 4.
  - Root cause of the specific 16:54 incident is not confirmed by this
    audit (the success payload is only rendered when `land()` returns
    Ok, so the "closed: true" text and the error came from different
    steps or invocations); the sites above are the candidates.
- Failure scenario: land ~A advances experimental and closes; a
  concurrent land ~B had just deleted its branch and rewritten
  packed-refs; ~A's later bare-name resolution fails; the coordinator's
  chain script sees exit 4 and stops the batch although ~A is landed.
- Fix direction: in frob-land, resolve the base once in `prepare` to
  `refs/heads/<base>` plus its Oid and pass the full name everywhere;
  split `publish` into "before CAS" (errors are errors) and "after CAS"
  (every failure becomes a warning, like `release`/`remove_worktree`
  already are); classify `GitError::Rev` as a refusal with a remedy, not
  internal; regression test that runs two lands back to back from one
  primary (acceptance criterion of ~BWMVSPZ).

#### M2. gob-exec timeouts do not hold on Windows (and on unix for setsid children): only the direct child is killed and the output reader joins block

- Where: crates/gob-exec/src/runner.rs `kill_group` non-unix 270-274,
  `collect` 216-219, call site 172-180.
- What is wrong: on non-unix `kill_group` is `child.kill()`; grandchildren
  (cargo -> rustc / test binaries, `uvx` -> python, `sh -c ...`) keep the
  inherited stdout/stderr pipes open; `collect` then `join`s the drain
  threads, which only finish at EOF, i.e. when every grandchild exits.
  On unix the process group kill covers most cases, but a descendant that
  calls `setsid` (some test runners, daemons) escapes it the same way.
- Failure scenario: Windows user runs evidence
  `--provider command --ref "cargo nextest run"` with a timeout; nextest
  hangs in a test; at the timeout gob-exec kills `cargo.exe` only;
  `cargo-nextest.exe` and the test binary keep the pipe; `frob` blocks
  indefinitely instead of reporting TimedOut. Same for
  `[check] sibling_timeout_secs` and `[[check.tool]]` stages.
- Fix direction: on Windows put the child in a Job Object with
  KILL_ON_JOB_CLOSE (crate `command-group` or `win32job`; unsafe stays
  out of the workspace); in both OSes bound the post-kill join (drop the
  reader handles after a grace period and return what was read).

#### M3. Ledger checkout sync after CAS can write an older version over a newer one in the primary working tree

- Where: crates/gob-git/src/ledger.rs `commit_paths_with` 180-185,
  `sync_checkout` 440-498, `sync_other_checkouts` 363-403.
- What is wrong: the CAS and the working-tree/index sync are separate
  critical sections. `sync_checkout` takes `index.lock` but writes the
  caller's planned blobs unconditionally; it never re-reads the ref tip.
- Failure scenario: writers A and B both write `tickets/X/ticket.md`
  (a land closing X while an evidence add or reconcile on X runs). A
  wins the CAS, B retries and wins on top of A, B syncs the checkout
  first, then A syncs: the working tree and index now hold A's
  ticket.md while HEAD holds B's. The primary shows a staged
  modification that reverts B; the next ledger write touching X from
  the primary fails `LocalEdits`, `git merge --ff-only` in land refuses
  (E-LAND-ADVANCE), and a human `git commit -a` would silently revert
  B. Window is small (milliseconds) but grows with lands running
  concurrently with agent writes.
- Fix direction: inside `sync_checkout`, after taking `index.lock`,
  read the current tip and skip any path whose tip blob differs from
  the blob being written (the newer writer syncs it); same in
  `sync_one_other`.

#### M4. crunk never applies exceptions

- Where: crates/crunk-check/src/product.rs `resolve_exceptions` 71-83
  (`apply_exceptions(raw, &[], &ctx)`).
- What is wrong: boundaries.md 3.2 says grimble and crunk parse
  exceptions and emit them; crunk passes an empty exception list, so a
  `crunk:accept COLOR001 because="..."` directive is ignored by
  standalone `crunk check`. grimble does bind them
  (grimble-check/src/product.rs:256).
- Failure scenario: a consumer accepts a known COLOR001 hit; `crunk
  check` still exits 1 and CI stays red; the only workaround is to edit
  code or drop the rule.
- Fix direction (structural): gob-check should own exception binding
  (directives are already product-neutral in gob-directives); make
  `Product::resolve_exceptions` a provided method that binds the
  product's namespace and only lets frob override for ticket-bound exits.
  That removes the per-product copy that let crunk skip it.

### Throughput and efficiency

#### M5. The land ratchet's base cache is keyed by commit oid, so in trunk mode it essentially never hits

- Where: crates/frob-land/src/ratchet.rs `base_findings` 91-121,
  `cache_key` 83-89, `run_at_base` 154-203; frob.toml:98-102
  (`ref = "refs/heads/experimental"`, `ref_mode = "trunk"`).
- What is wrong: the ledger ref is the base branch, so every ticket
  event (including the previous land's own close) is a new base commit.
  The cache file is `<oid>-<key>.json`; the next land sees a new oid and
  runs a full unscoped `frob check` in a throwaway worktree, including
  every `[[check.tool]]` stage (cargo fmt, clippy, `cargo dev gen
  --check`, zizmor, actionlint, deny, shear, typos).
  notes/coordinator.md 2026-10-06: "no ledger writes while a land runs
  (each write forces a ~7 min re-check)".
- Failure scenario: two lands in a row with one `ticket update` between
  them: both pay the full base check although no code changed.
- Fix direction: key the code-rule base set by a digest of the base
  tree with the ledger directory removed (the tree oids of the other
  top-level entries plus the config digest); compute ledger-family
  findings (TICK, PM, REF over ledger paths) for the exact oid
  separately, which is cheap. This is the single highest-value change
  for land throughput.

#### M6. `ticket doable` is O(candidates x live leases x repository files) with glob sets rebuilt per pair (likely cause of ~ZZQ6PA9, 23 s)

- Where: crates/frob-ledger/src/ops.rs `doable` 201-226;
  crates/frob-lease/src/guard.rs `is_free` 46-66;
  crates/frob-lease/src/overlap.rs `scopes_overlap` 322-357,
  `Resolver::resolve` 276-291, `all_files` 255-269.
- What is wrong: for each todo candidate and each live lease,
  `scopes_overlap` normalizes both scopes, compiles two `GlobSet`s and
  filters the full walked file list twice. The walk includes the ledger
  (12,078 tracked files, 7,403 of them under tickets/). With ~300
  candidates and 2 leases that is ~1,200 globset compiles and ~14
  million glob matches in a debug build. Also one `index.get` per
  candidate.
- Failure scenario: every `frob ticket doable`, `board` NEXT and
  `work` admission check on this repository.
- Fix direction: resolve each live lease's file set once per command;
  compile each candidate's glob set once; exclude the ledger directory
  from the resolver walk (ledger paths are never leasable scope); a
  candidate whose globs fail the textual test against every lease skips
  the file pass entirely.

#### M7. Rules and checks read files straight from disk instead of the snapshot's content

- Where (non-exhaustive): crates/frob-obligations/src/lib.rs:300
  (`std::fs::read` then `bytes.clone()` for every file), doc.rs:133,
  inv.rs:153, collect.rs:92, sibling.rs:41;
  crates/frob-check/src/snapshot.rs:277, product.rs:359, verb.rs:156;
  crates/gob-check/src/filecheck.rs:294 and 353, defs.rs:145,
  tools.rs:135, repo.rs:160; crates/crunk-check/src/rules/color001.rs:108;
  crates/grimble-check/src/lib.rs:206.
- What is wrong: gob-walk already reads every file (through
  `gob_git::WorktreeReader`, crates/gob-walk/src/content.rs:8) to digest
  it for the cache; rules then re-read the same files from disk by
  path, several times per check, with no shared size cap or encoding
  policy.
- Failure scenario: a file is saved between the walk and a rule's read
  during a 20-30 s cold check: the finding is computed on the new text
  but cached under the old digest, so the next warm run replays a
  finding for content it was not computed from (EB0S8DF is the
  `--fix` cousin of this). In consumer repositories with eol or filter
  attributes the walk digest and the rule text also differ.
- Fix direction: `Snapshot::text(file) -> Arc<str>` memoized from the
  walk's bytes; ban `std::fs::read*` in rule and check crates with
  clippy `disallowed-methods` (the same mechanism D93 uses for clocks),
  allow-listing gob-walk and gob-fs.

### Structure and build

#### M8. gob-walk depends on gob-git, which drags gix (54 crates) under the pure model crates and onto every product's critical path

- Where: crates/gob-walk/Cargo.toml:16; crates/gob-walk/src/content.rs:8
  (only `WorktreeReader`, `WorktreeSource`); also crates/gob-lock/src/file.rs:18
  (gob-lock depends on gob-ir for one `u32` constant) and
  crates/gob-cache/src/lib.rs:222-240 (gob-cache depends on gob-exec for
  `canonical()` and re-implements git common-dir discovery by hand,
  ignoring `GIT_DIR`, bare repositories and `core.worktree`).
- What is wrong: gob-ir (the universal model), gob-symbols, gob-lock,
  gob-plan, gob-frameworks, grimble-model and crunk-check all compile
  gix (`cargo tree -p gob-ir`: 251 unique deps). The serial critical
  path of every binary starts with it:
  frob-cli: gob-log -> gob-exec -> gob-git -> gob-walk -> gob-ir ->
  gob-symbols -> gob-check -> frob-obligations -> frob-check ->
  frob-land -> frob-cli (11 crates, ~59k source lines);
  crunk (a design-system linter): 9 crates, the same first six.
- Consequence: no parallelism between gix and the model/adapter crates
  on a clean or CI build; any gob-git edit rebuilds the whole model
  stack.
- Fix direction: move the reader trait into gob-walk (it already has
  `ContentSource`); gob-git implements it; check crates inject the git
  reader. Move `DIGEST_SCHEME` into gob-caps (leaf) and drop
  gob-lock -> gob-ir. Move `canonical` and `git_common_dir` to gob-fs
  (or the planned gob-path) and have gob-cache use gob-git's
  `common_dir` instead of its own parser.

#### M9. The layering rule that boundaries.md section 6 says is "enforced by a repo-internal rule over Cargo metadata" does not exist, and the graph violates it

- Where: docs/design/boundaries.md section 6; no such rule in
  crates/gob-dev/src (grep for metadata/layer finds only publish and
  wheel code).
- Violations found (cargo metadata):
  - gob-* depends on product crates: gob-dev -> frob-cli, frob-check,
    frob-evidence, frob-ledger, grimble-check, crunk-check, crunk-spec
    (crates/gob-dev/Cargo.toml:23-38); dev-deps gob-macros -> frob-ledger,
    gob-product -> crunk-check.
  - Substrate order inverted: design says gob-rules uses gob-ir's
    lattice (above it); code has gob-ir -> gob-rules
    (crates/gob-ir/Cargo.toml:13, eval/program.rs:11).
  - Product knowledge in substrate: gob-walk reads `frob.toml [tickets]
    dir` (crates/gob-walk/src/role.rs:70-85, silent default on any parse
    error).
  - Intra-frob inversion: frob-lease -> frob-release only for the
    changelog fragment file-name parser (crates/frob-lease/src/overlap.rs:17,
    Cargo.toml:14), pulling semver/similar/toml_edit/frob-pm under leases.
  - frob-cli dev-depends on the grimble and crunk binaries
    (crates/frob/Cargo.toml dev-dependencies).
- Consequence: the design's main structural guarantee is unchecked, so
  inversions accumulate (~M8WETW7 is one already filed).
- Fix direction: a gob-dev test over `cargo metadata` with an explicit
  layer table (leaf, substrate tiers, product, binary, dev-only) and an
  allow list that only shrinks; then fix each item (fragment naming
  into frob-ledger; ledger dir passed into gob-walk `Roles` by the
  caller; gob-ir/gob-rules order decided and the doc updated).

#### M10. gob-dev mixes a task runner with product-aware generation, so every `cargo dev` step builds the whole product graph, twice on Windows

- Where: crates/gob-dev/Cargo.toml:23-38; .cargo/config.toml
  (`dev` and `dev-isolated` aliases); .github/workflows/ci.yml:52-104.
- What is wrong: `ci.rs`, `isolation.rs`, `publish.rs` use no product
  crate; only `products.rs`, `import_v1*.rs`, `lib.rs`, `main.rs` do.
  Yet `cargo dev ci --step fmt` compiles frob-cli, frob-check,
  grimble-check and crunk-check before running `cargo fmt --check`, and
  on Windows `dev-isolated` builds that whole graph a second time into
  target/dev-tool. CI log of run 37657654375: "rustfmt (Windows,
  isolated tool)" 93 s and Linux "rustfmt" 40 s, both mostly building
  gob-dev.
- Fix direction: split into `gob-xtask` (ci steps, isolation, publish,
  profile; depends on gob-exec/gob-log/toml only) and `gob-gen` (gen,
  import-v1; depends on products), with the ci `gen` step calling
  `cargo run -p gob-gen`. The isolated build becomes seconds, the
  Windows-locked-exe problem disappears for everything except gen, and
  ~M8WETW7 is solved as a side effect.

#### M11. Six crates (~14k source lines) have no consumer but are built, linted, documented, tested and published every release

- Where (reverse deps = 0): gob-plan (9,013 lines, the GRL
  compiler/executor), gob-frameworks (1,719), crunk-tailwind (1,016),
  frob-gh (823; reqwest + rustls + ring + tokio), gob-trust (769),
  gob-packs (492).
- Consequence: workspace clippy/doc/nextest pay for them on both OSes;
  their public APIs are frozen on crates.io in lockstep (the 0.532.0
  publish hit 429s across 43 crates); the dependency graph suggests
  capabilities that no binary has.
- Fix direction: `publish = false` until a product links each one (one
  line per manifest, plus the releases.md lockstep list); wire frob-gh
  first (H1). Keep them in CI, but they stop costing releases.

#### M12. gob-symbols is a 22,414-line crate holding every language adapter with no features; gob-languages features exist but every consumer takes all grammars

- Where: crates/gob-symbols/src (rust.rs 3,561; graph.rs 2,757;
  typescript/fold.rs 2,049; csharp.rs 1,497; python.rs 1,292; nodejs.rs
  1,066; dotnet.rs 886; graph/csharp.rs 858; css, html, yaml, markdown);
  crates/gob-symbols/Cargo.toml has no `[features]`;
  crates/gob-languages/Cargo.toml `default` enables all 11 grammars and
  none of its 9 dependents sets `default-features = false`.
- Consequence: an edit to the C# adapter recompiles gob-symbols and its
  14 dependents (gob-check, every frob-*, grimble-*, crunk-check);
  crunk compiles the C#, Python and Rust grammars it never uses.
- Fix direction: keep gob-symbols as the core (model, symref, registry,
  pipeline, graph core) and move each adapter family into its own crate
  (`gob-lang-rust`, `gob-lang-web` for TS/JS/CSS/HTML, `gob-lang-python`,
  `gob-lang-dotnet`, `gob-lang-data` for markdown/toml/yaml) registered
  through the existing inventory registry (registry.rs); products select
  adapters by feature.

### Programming ergonomics (owner scope)

#### M13. Configuration is parsed many times per command and `[tickets]` has four independent parsers

- Where: crates/frob/src/config.rs:105-140 (`FrobConfig::load`: 11
  `gob_config::load` calls; each re-reads and re-parses frob.toml,
  crates/gob-config/src/load.rs:55-68); crates/frob-evidence/src/workspace.rs:94-130
  (hand-walked `toml::Table`); crates/frob-worktree/src/config.rs:67-90
  (serde `RawFile`); crates/gob-walk/src/role.rs:70-85 (dir only, silent
  default); crates/frob-check/src/snapshot.rs:331 (another raw read);
  crates/frob-land/src/land.rs:327-343 (GC reloads ledger, worktree and
  gc config after a land that already had them).
- Root cause: the validated `TicketsTable` and `GitTable` live in the
  binary crate (frob-cli), so library crates that need ledger settings
  cannot use them and each writes its own parser.
- Failure scenario: a key added to `[tickets]` (say a future
  `ref_mode` value) must be taught to four parsers; the hand parsers
  disagree on unknown keys and wrong types (frob-evidence errors,
  frob-worktree ignores, gob-walk silently defaults), so the same
  frob.toml can make `frob check` treat a different directory as the
  ledger than `frob land` does.
- Fix direction: move `TicketsTable` and `GitTable` into frob-ledger
  with `LedgerConfig::load(&doc)`; add `gob_config::Document` (parsed
  once, `doc.table::<T>()`) and pass it down; delete the three hand
  parsers.

#### M14. No per-command session: every verb rediscovers the repository and reopens ledger, leases and config; three different "Workspace" types

- Where: crates/gob-cli/src/context.rs:35-52 (`Context` carries cwd,
  output flags and clock only); 47 `Repo::discover` / `Ledger::open` /
  `Workspace::open` sites, 8 in crates/frob-land/src/land.rs alone;
  `frob_evidence::Workspace` (frob-evidence/src/workspace.rs:20) is used
  by frob-land as its general workspace; `frob_worktree::Workspace<'a>`
  (frob-worktree/src/work.rs:82); `frob_cli::Located`
  (frob/src/workspace.rs).
- Consequence: duplicated open/refusal code per verb, extra gix opens
  and config parses per command, inconsistent error mapping
  (land maps `Repo::discover` failure to `LandError::Config`,
  land.rs:59 and 118, which renders as "E-CONFIG fix frob.toml"), and a
  new verb author must learn which Workspace to use.
- Fix direction: one `Session` type in frob-ledger (or a small
  `frob-session` crate below frob-lease) with lazily opened repo, config
  Document, ledger, lease store and cache, built once per command and
  handed to verbs; frob-evidence, frob-worktree and frob-land take
  `&Session`.

#### M15. Every verb declares its flags twice by hand (clap builder plus string lookups)

- Where: crates/gob-cli/src/command.rs:17-41 (`configure` and
  `from_matches`); 72 `from_matches` implementations; e.g.
  crates/frob-land/src/verb.rs:30-126 (about 100 lines for 8 flags);
  copied helpers `text()`/`flag()` in frob-land/src/verb.rs:23,
  frob-worktree/src/verbs.rs:146, frob-evidence/src/verbs.rs:222,
  `text_flag` in frob/src/ticket/mod.rs:70.
- Consequence: flag ids are strings in two places; a typo is a runtime
  panic or a silently absent value; the most common change in the repo
  (adding or renaming a flag) touches two places plus help text.
- Fix direction: verb structs `#[derive(clap::Args)]`; give `Command`
  provided `configure`/`from_matches` via `Args::augment_args` /
  `FromArgMatches`; keep `gob_cli::Command` derive for metadata only.
  Migrate verbs incrementally; cross-flag validation stays in a
  `validate()` hook.

#### M16. Two rule registration systems coexist; D107 has zero rules migrated

- Where: crates/frob-check/src/product_rules.rs:1-11 ("No rule crate has
  moved to `#[rule]` yet, so the list is empty"), the same empty lists
  in grimble-check and crunk-check; rules still register through
  inventory and the startup `verify_unique` (crates/gob-product/src/lib.rs:36-42).
- Consequence: adding a frob rule today means a meta struct in
  `rules.rs`, logic in a module, manual wiring in
  `evaluate`/`file_rules` (frob-obligations/src/lib.rs:276-340), a page,
  and knowing which of two mechanisms applies; the promised compile-time
  uniqueness and "no registration step" do not exist yet.
- Fix direction: finish one product end to end (frob-obligations, the
  largest family set) before adding more rules or GRL work; then delete
  the inventory path (~H5W28EA).

#### M17. Tests: many integration-test binaries per crate, and the frob CLI tests spawn the debug binary although an in-process runner exists

- Where: integration test files per crate: frob-cli 32, gob-symbols 14,
  frob-check 14, frob-release 12, gob-ir 8 (each a separately linked
  binary); crates/frob/tests/common/mod.rs:69-72 (`frob_command` spawns
  `cargo_bin("frob")`, 35 call sites) vs `gob_cli::run_for_test`
  (crates/gob-cli/src/cli.rs:589, 4 call sites in frob/tests); about 10
  frob test files define their own `fn frob(dir, args)` spawn helper.
- Consequence: build-test-ci.md 5 states the suite is bound by the CPU
