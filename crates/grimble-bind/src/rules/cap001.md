# CAP001 cap-undeclared

Code a node owns uses a capability atom the node does not grant.

## What it does

Deny by default (binding.md 7.2 item 3): fires once per node and atom when a call in Must-owned code matches the callee vocabulary of the atom for its language and no `may` of the node covers it (the atom itself or its parent, at the grant's `at` files). One finding per node and atom, anchored at the node; the message lists every use as `file:line callee` and the narrowest grant that would allow it (`may fs.write("<observed path>") at "<file>::<symbol>";`). `grimble why <file:line|file::symbol>` prints the verdict for one call site. An exception names its atom and expires: `accept CAP001 atom="process.spawn" until=2027-01-31 because="...";` silences only that atom (an alias such as `exec` resolves to its canonical atom) until the date, then the use fires again; an `accept CAP001` without `atom=` or `until=` is an MDL013 error. The exception itself needs an attester's ack (CAP005). Unresolved when the code is owned only at May. An excuse never hides a use (CAP004 is not implemented yet).

## Why it matters

A capability the model does not grant is one no review of the model ever saw, so the node can do more than it declares.

## Remedy

Copy the suggested narrowest `may ... at "<file>::<symbol>"` grant into the node, or remove the use. Avoid a bare `may <atom>` on the node, which allows the atom everywhere in it.

## Examples

### Fires case 1

```grmb expect=fire file=design/m.grmb config="py"
grimble = "2";
module m;

node a : trusted {
  owns "src/x.py";
}
node d : trusted {
  owns "design/**";
}
```

### Clean case 2

```grmb expect=clean file=design/m.grmb config="py"
grimble = "2";
module m;

node a : trusted {
  owns "src/x.py";
  may fs.read;
  may exec;
  may net.listen;
}
node d : trusted {
  owns "design/**";
}
```
