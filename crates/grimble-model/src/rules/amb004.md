# AMB004 amb-retry-product

An arm `retry` of a system step is also repeated by an applying ambient `retry`, so the attempts multiply.

## What it does

An ambient `retry max N` repeats a failing system step; an arm `retry STEP max M` on the same step repeats it again. The finding names the policy and the product `N * M` of the two bounds. One finding is raised per arm retry and applying policy: the scenario's own `ambient` override (else the system policy) and the override of every scenario that includes it. It is skipped when a bound does not parse (AMB003 owns that) and for a `restart` policy.

## Why it matters

Two layers of retry on one step can hammer a failing dependency far past either bound, and the real attempt count is nowhere written down.

## Remedy

Drop one of the two retries, or lower the bounds so their product is acceptable.

## Examples

### Fires case 1

```grmb expect=fire file=design/model.grmb
grimble = "2";
module m;

system s {
  ambient retry max 2 { verified_by "tests/a.py"; }
  actor u : human;
  step u.go;
  step system.flaky -> { ok, bad };

  scenario t {
    u.go -> system.flaky => {
      ok -> end ok;
      bad -> retry system.flaky max 3;
    }
  }
}
```
