---
id: INV-001
statement: Lock writes are atomic; a crashed frob never truncates frob.lock
criticality: high
evidence:
  - tests/test_graph_lock.py::TestWriteLock::test_write_lock_is_atomic
---

`write_lock` must never leave `frob.lock` half-written: a process killed
mid-write (or a concurrent reader) must see either the old complete file or
the new complete file, never a truncated one. `frob.lock` is the ack ledger
DRIFT001 compares against, so a torn write would silently widen or narrow
drift detection depending on which half survived.

The implementation writes to a temp file in the same directory and calls
`os.replace` (atomic rename on POSIX and Windows NTFS) to publish it.
`test_write_lock_is_atomic` spies on `frob.graph.lock.os.replace` and
asserts it is called exactly once, with the final argument equal to the
real lock path -- proving the write goes through the atomic-rename seam
and not a direct in-place write.
