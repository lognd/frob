---
id: INV-037
statement: should_color's NO_COLOR/FORCE_COLOR/TTY precedence is total and
  deterministic -- NO_COLOR always wins over FORCE_COLOR, and color falls
  back to the TTY/TERM check only once both env vars are absent
criticality: medium
evidence:
  - tests/unit/test_logging_module.py::test_should_color_respects_no_color
  - tests/unit/test_logging_module.py::test_should_color_respects_force_color
  - tests/unit/test_logging_module.py::test_should_color_no_color_wins_over_force_color
  - tests/unit/test_logging_module.py::test_should_color_term_dumb_disables_color_on_a_tty
---

`frob.logging.color.should_color` documents a strict precedence: `NO_COLOR`
(any value) always disables color regardless of any other signal;
`FORCE_COLOR` (absent an overriding `NO_COLOR`) always enables it; only
once both are absent does color fall back to "stream is a TTY and TERM is
not dumb". A second, drifted `should_color` implementation elsewhere (or an
ordering bug in this one) would silently desync color behavior across CLI
surfaces -- exactly the class of bug this module's own docstring calls out
as the reason only one implementation may exist.

Note this is a DIFFERENT function from `frob.render._color.resolve_color`
(a separate, wider precedence covering CLI flags, already covered by its
own `INV-020`) -- `should_color` is the narrower, log-formatter-facing
decision with no knowledge of CLI flags.

`test_should_color_respects_no_color` and
`test_should_color_respects_force_color` prove each signal individually;
`test_should_color_no_color_wins_over_force_color` proves the ORDER (both
set simultaneously must still resolve to "never"); and
`test_should_color_term_dumb_disables_color_on_a_tty` proves the fallback
branch's own TERM=dumb carve-out on an otherwise-TTY stream.
</content>
