id: INV-037
statement: should_color's NO_COLOR/FORCE_COLOR/TTY precedence is total and
  deterministic -- NO_COLOR always wins over FORCE_COLOR, FORCE_COLOR always
  wins over the TTY/TERM check, and color is never enabled outside that order
criticality: medium
evidence:
  - tests/unit/test_render.py::TestResolveColor::test_no_color_flag_wins_over_everything
  - tests/unit/test_render.py::TestResolveColor::test_color_always_forces_color_when_piped
  - tests/unit/test_render.py::TestResolveColor::test_no_color_env_disables_color_on_a_tty
  - tests/unit/test_render.py::TestResolveColor::test_frob_no_color_env_disables_color_on_a_tty
  - tests/unit/test_render.py::TestResolveColor::test_clicolor_force_colors_a_non_tty_stream
  - tests/unit/test_render.py::TestResolveColor::test_term_dumb_disables_color_on_a_tty
---

`frob.logging.color.should_color` documents a strict precedence: `NO_COLOR`
(any value) always disables color regardless of any other signal;
`FORCE_COLOR` (absent an overriding `NO_COLOR`) always enables it regardless
of TTY-ness; only once both are absent does color fall back to "stream is a
TTY and TERM is not dumb". A second, drifted `should_color` implementation
elsewhere (or an ordering bug in this one) would silently desync color
behavior across CLI surfaces -- exactly the class of bug this module's own
docstring calls out as the reason only one implementation may exist.

`TestResolveColor` in `tests/unit/test_render.py` exercises every branch of
the precedence order directly against `should_color`, including the
override cases (`NO_COLOR` set alongside a TTY stream that would otherwise
color, `FORCE_COLOR`/`CLICOLOR_FORCE` set against a non-TTY stream that
would otherwise not) that actually prove the ORDER, not just each signal in
isolation.
