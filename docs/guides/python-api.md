# Python API reference

frob's advertised public Python API: every name listed in a package's own
`__all__` (`src/frob/**/__init__.py`), for every package whose own dotted
path has no underscore-prefixed segment (an underscore-prefixed package,
e.g. `frob._cli_parsers`, is an implementation detail regardless of
whether its `__init__.py` happens to declare `__all__`).

THIS LIST IS GENERATED, NOT HAND-MAINTAINED: it is the same
`discover_public_api` function `tests/system/test_public_api_from_wheel.py`
uses to prove every one of these names actually imports from a real BUILT
WHEEL (frob + its `frob-core`/`strata-core` native dependencies), not
merely from this source tree -- see that test's module docstring for why
a tree-only check cannot catch the class of defect this guards against
(a packaging claim true in config, false in the artifact, invisible for
months). Re-run `discover_public_api(repo_root)` (import it directly from
that test module) to regenerate this list if it drifts.

## Installing it (T-4150)

frob is currently installed as an isolated `uv tool`, which by design
puts it on its own interpreter path -- a consumer project's own
interpreter cannot see it via a normal dependency declaration until a
release carrying the current API is published to a registry (the
owner's decision, not made by this ticket). Until then, importing frob
from another project's code requires that project's own environment to
have frob (and `frob-core`/`strata-core`) installed as real dependencies,
not merely available as a CLI tool.

A verb that reports the running frob's own interpreter/site-packages
path (making a tool-install still usable from another project without a
fragile `shutil.which`-based shim) is tracked separately and intentionally
not built by this ticket -- see T-4150's own coordinator note on why the
registration surface for a new verb needed its own measurement first.
