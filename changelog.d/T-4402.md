Root cause: `_run_with_stale_reconnect` deliberately never closes the CALLER's own connection when it is merely "stranded" (bound to a replaced-away file) -- closing it would turn the caller's next ordinary use into a ProgrammingError (see `_reopen_without_closing`'s own docstring, T-3669). That posture is safe on POSIX because `_recreate` renames the corrupt db ASIDE (T-3607) rather than unlinking it in place, so a still-open caller fd stays bound to the old, harmlessly-quarantined inode. On win32 the platform itself makes that posture unsafe instead of merely impolite: `_recreate`'s `_replace_with_retry` calls os.replace(tmp_path, path), and Windows refuses to replace a path with ANY open handle on it, unlike POSIX rename.
