Fix is platform-branched, not a blanket rewrite: dotnet already has a win32 PATHEXT-aware resolver in gitio.run_argv (_resolve_win32_executable, T-3799) that finds a bare "dotnet" -> "dotnet.cmd" via shutil.which, so writing dotnet.cmd on win32 is sufficient there. Unity's fixture instead returns its own path directly via UNITY_PATH (never resolved through run_argv's bare-name lookup), so its win32 branch must itself be named Unity.cmd -- the returned path IS what gets spawned. Both branches emit CRLF batch-file equivalents of the POSIX shell logic (parse args, copy the named static fixture to the requested output path, exit with the given code). Verified all 19 tests in both files still pass unchanged on this Linux host (the sys.platform=="win32" branch is dead code here, by construction) -- could not execute-verify the Windows branch itself on this host, so the fix is code-reviewed against Windows CreateProcess/ PATHEXT semantics, not test-run on Windows.
