WHY: Windows CI (run 35476139324) stalls past 600s in tests/gates_suite/test_tick.py::
TestTick008UnknownLedgerFields::test_real_repo_ledger_is_tick008_clean. Reproduced locally via
`winrun ~/bin/winrun .venv/Scripts/python.exe -X faulthandler -m pytest ... --timeout 300
--timeout-method=thread`: the faulthandler dump shows the hang inside `tickets_gate ->
_tick007_undispatched_stale -> doable() -> leased_by() -> _leased_by_one_holder() ->
frob.tickets._leases.same_worktree_lease() -> frob.gitio.repo_root(root) -> subprocess.run(git
rev-parse --show-toplevel)`. `repo_root` had NO caching at all, and `same_worktree_lease` is
called once per (ticket, holder) pair inside `leased_by`'s inner loop, itself called once per
ticket inside `doable()`'s main loop -- against this repo's live ~1171-ticket queue, that is on
the order of hundreds of thousands of subprocess spawns of the SAME unchanging `root` within one
`doable()` invocation. Cheap enough (fork) to merely be slow on Linux/macOS, but Windows process
creation is dramatically more expensive, so this is what stalls CI there specifically. This is the
same class of bug T-0453/T-0773 already fixed for `scope_breadth_context`/`_all_leases` in
`frob.tickets._doable` -- `same_worktree_lease`'s own `repo_root` call was missed by that
precedent. Classification (a), real bug.

*** IMPORTANT -- THIS FIX ALONE DOES NOT FULLY RESOLVE THE STALL ***
After this fix, re-running the target test locally (Linux, single worker) still runs far longer
than expected and a faulthandler/pytest-timeout dump still shows the SAME call chain, now stuck
inside `Path.resolve()` (my cache's key-computation line) rather than the git subprocess spawn.
Root cause 2, NOT fixed by this ticket: `same_worktree_lease` ALSO calls `read_all_leases(root)`
fresh on every one of those same (ticket, holder) pairs, and `read_all_leases` does a fresh
`os.stat`-based liveness check per lease (`_probe_worktree_liveness`) on every call, BY DESIGN
(its docstring explicitly forbids caching this across calls, for freshness against `frob.serve`'s
daemon and sibling processes). So the same tickets x holders multiplier now applies to a full
leases-directory rescan instead of a git spawn -- smaller per-call cost (stat vs. subprocess) but
still applied astronomically often. I confirmed this is live and severe on this actual box: an
unrelated `frob ticket new`/`promote` call I ran during this same pass took several CPU-minutes in
apparent I/O-bound work, consistent with this exact code path under this repo's real ticket-queue
size. Filed as a separate follow-up (see below) rather than blindly caching `read_all_leases`
myself, since its own docstring is explicit that liveness must NOT be cached across calls without
a considered design decision (a stale-lease-not-detected bug there risks two agents silently
editing the same file).

Filed: T-5075 (bug, parent T-4806) -- "same_worktree_lease rescans all leases on every
ticket-holder pair", scoped to src/frob/tickets/_leases.py (confirmed unleased at filing time),

precomputed leases snapshot (mirroring the `all_leases` pattern `_doable.py` already uses, but

cache to `same_worktree_lease` itself.
