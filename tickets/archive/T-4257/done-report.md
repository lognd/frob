Lint-diff-attribution: _ruff_baseline_diagnostic_identities resolves ruff via `uv run --project <detached-snapshot-worktree>` -- a worktree with no .venv of its own, so uv falls back to bare-PATH resolution outside any project. MEASURED on Windows: this fails outright ("Failed to spawn: ruff", no shell activation puts a venv's Scripts/ on PATH for a plain interpreter spawn) while it happens to find a global ruff on Linux dev boxes. The resulting empty stdout was ALSO being parsed as a successful run producing one synthetic "malformed JSON" diagnostic (tool_parse_failure_result's contract for a truncated/corrupt payload, not "no payload at all"), and since both the current-pass and baseline-pass spawns failed identically, their synthetic diagnostics compared as pre-existing and silently swallowed the land refusal this gate exists to produce. Fixed via a resolve_root split (the baseline pass resolves ruff from the real owning worktree, which has a venv, while still scanning the snapshot's files) plus treating empty stdout as "spawn unavailable" (None) rather than a parse failure, plus a sys.executable -m ruff fallback for the genuinely-not-a-uv-project case the test fixture itself models. Release-bump: _apply_composed_diff_onto_scratch wrote its git-diff patch file via Path.write_text's default text mode, which translates bare \n to CRLF on Windows -- corrupting the LF-terminated diff's lines, which git apply then reproduced verbatim into the target file, making a content-identical no-op bump look like a real tree change. Fixed via newline="" on that write (the load-bearing fix, confirmed by reverting it and reproducing the original failure), plus -c core.autocrlf=false on the scratch worktree's own `git worktree add`/`git apply` invocations as defense in depth (the account's global core.autocrlf=true was independently confirmed present and is a plausible latent risk even though it was not this bug's actual proximate cause).

Strata GIL timeout: obtained a real stack via `Windows fatal exception: stack overflow` in stderr under pytest-timeout's thread-method watchdog (no faulthandler dump was even needed -- Python's own crash handler printed the native stack directly). The stack showed the main thread crashing INSIDE worst_age_impl's recursive SCC/topo-sort DP, at ~4.5s into a call that takes ~6s to complete on Linux -- a genuine STATUS_STACK_OVERFLOW crash, not a hang and not merely-slow-but-complete (elapsed stayed under the timeout's own generous 30s bound, so the watchdog was never even the bottleneck). Root cause: Windows' default thread stack (1 MiB) is far smaller than Linux's (8 MiB), and a 6000-hop input recurses deep enough to exceed it. Fixed via run_on_big_stack: a dedicated 64 MiB worker thread wraps all four allow_threads-releasing kernels (reachable/worst_age/propagated_demand/vmodel_check), sidestepping the platform stack-size default entirely.
